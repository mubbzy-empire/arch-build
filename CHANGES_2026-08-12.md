# Changes made in this session

Scope note up front: this was done without a working build/network environment,
so nothing here has been run in a browser. Every plain-JS file
(`buildParts.js`, `skyEnvironment.js`, `aiService.js`) passed a Node syntax
check; the JSX files (`ModelViewer.jsx`, `SceneViewer.jsx`) were reviewed by
hand and brace/paren-balanced but not compiled. Please `npm install` and
smoke-test before deploying — if anything throws in the console, send me the
error and the model/estate that triggered it and I'll fix it directly.

## What was already there (didn't need rebuilding)
The 3D engine was already well ahead of what the screenshots suggested:
real CSG-cut door/window openings with frames, actual hip roofs (not cone
approximations), string-course trim between floors, a base plinth,
multi-story stacking with per-floor envelopes, balconies with railings, and
interior partition walls with real connecting doors. The blocky look in your
screenshots is the *fallback* path — what renders when the AI's response is
under-detailed and the app falls back to a plain grid of partitions with flat
cream/gray colors. So this pass focused on visual quality (color, corner
detail, site dressing) and the three specific features you asked for, not a
ground-up rebuild.

## New features
- **Garage** — no new part type. Any `door` opening ≥2.2m wide is now
  automatically rendered as a sectional garage door (horizontal panel lines,
  no handle) instead of a house door. The AI prompt now tells the model to
  size a garage door this wide when a garage is mentioned.
- **Swimming pool** — new `pool` part group (`buildPoolMesh` in
  `buildParts.js`): a tiled sunken basin, a coping/deck rim, and a water
  surface, all built from one part (`size: [width, waterDepth, length]`).
  The AI prompt documents this and is told to only add it when asked.
- **Compound wall for every model, not just estates** — `buildCompoundWall()`
  in `skyEnvironment.js` builds a perimeter wall with corner pillars and a
  two-leaf bar gate. It's now called from both `ModelViewer.jsx` (single
  building) and `SceneViewer.jsx` (estate), so a lone bungalow gets the same
  walled-compound treatment an estate always did.
- **Storey buildings** — already fully supported (per-floor envelopes, trim,
  balconies); no changes were needed here beyond making sure the new corner
  pilasters apply per floor too.

## Visual quality changes (the "match the reference photos" part)
- **Corner pilasters** — every floor of every building now automatically
  gets banded, dark corner columns (`addCornerPilasters`), applied
  procedurally regardless of what the AI/offline template specified. This is
  the single biggest driver of the "designed elevation" look in your
  reference images.
- **Two-tone exterior palette** — offline templates switched from tan/brown
  to a blue body + darker accent scheme matching your reference photos; the
  AI prompt now explicitly asks Gemini for a light body color with a
  noticeably deeper accent shade, and tells it NOT to draw its own boundary
  walls/corner posts since those are now automatic.
- **Interior finish** — partition walls now get a thin skirting board at
  the base (`addSkirtingForWall`); fallback-generated partition walls switched
  from tan to a clean off-white finish tone to match the lighter exterior
  palette.

## 2026-08-12, second pass — fixes from live screenshots

You sent screenshots of the deployed model (AI-generated "Blueprint Layout
House"). Three real problems, diagnosed and fixed:

1. **Compound wall was invisible** — it *was* being built, just far outside
   the camera's default framing (the camera only fit itself to the bare
   building, and the wall was sized ~2.2× the building's width away from
   center). Fixed: the compound is now sized tighter to the building
   (`maxDim * 1.45` instead of `radius * 4.4`), and the camera distance
   calculation now accounts for the compound's size too, so the wall/gate
   are inside the frame on first load.
2. **Interior partition walls rendered bright golden-wood** — this is the
   generic "wood" material's default tint (`0xb98a55`) showing through
   because the AI (correctly, per the schema) tags partition walls as
   material "wood" but usually doesn't set an explicit color. Fixed: any
   wall-shaped `interior` part without an explicit color now defaults to a
   clean off-white (`#eef0ea`) instead of raw wood tone; floor slabs
   (flat, not wall-shaped) are untouched.
3. **Interior looked almost black once the roof was hidden** — the
   interior fill light's "on" intensity was `1.2`, a value left over from
   before this three.js version switched to physically-correct (candela)
   lighting units, where `1.2` is essentially imperceptible. Bumped to `90`
   with `decay: 1` (linear falloff) so it actually lights a room-scale
   interior. This is an educated, untested guess at the right order of
   magnitude — may still need tuning once you can see it rendered.

Still unresolved: there's a dark vertical rod floating in the middle of the
interior in your first screenshot that I can't explain from the code I've
touched — could be a part the AI generated (a column/pipe) for this
specific blueprint. Tap it in the viewer ("tap a part for details") and
tell me what group/room it reports and I can track it down.

## Session 2: render-quality pass to match a target reference photo

You shared a rendered reference image (two-tone blue siding, dark navy hip
roof with a crisp white eave trim, white window frames, stone-paved drive,
trees, dramatic sky) and asked for the model's exterior/interior quality to
be rebuilt to that bar, not just re-tinted. Changes, all in the render
engine itself (`buildParts.js`, `skyEnvironment.js`) so every generated
building benefits, not one instance:

- **Painted-siding wall texture** (`getSidingTexture` / `makeSidingMaterial`
  in `buildParts.js`): every exterior "structure" wall is now a procedurally
  generated, color-tinted board-siding texture (vertical panel seams +
  faint weathering streaks) instead of one flat color. Tinted per-part from
  whatever hex color the AI/swatch picker chose, cached per color.
- **Shingled roof texture** (`getRoofTexture` / `makeRoofMaterial`): roofs
  get horizontal coursing lines + speckle instead of a flat color, tinted
  the same way (defaults to a dark navy-slate if no color is set, matching
  the reference roof tone).
- **White eave fascia trim** (`buildRoofFascia`): a new thin painted board
  now traces the full eave perimeter of every hip roof, giving the crisp
  light-colored line that separates roof from wall in the reference photo —
  previously the roof edge just met the wall with no trim at all.
- **UV fix**: the hand-built hip-roof geometry never had UV coordinates
  (fine when it only used flat colors); added a planar XZ UV pass so the
  new shingle texture actually maps onto it instead of rendering blank.
- **Window/door frame tone** bumped from a dull cream to a cleaner white
  (`#f4f1e6`) to match the fascia.
- **Sky**: replaced the plain 4-stop blue gradient with a moodier one plus
  soft cloud masses (shaded undersides + lit tops), closer to the reference
  photo's sky than the old flat cartoon gradient.
- **Trees**: `buildOutdoorGround` now scatters four simple two-tone
  trunk+canopy trees around the plot corners, scaled to the plot size —
  the reference has trees flanking the house and the model previously had
  none. Cached geometry, per-call materials, all flat children so the
  viewer's existing ground cleanup (`ground.children.forEach(...dispose)`)
  reaches them without changes elsewhere.
- Manual-modeler walls (`buildWallWithOpenings`) and every AI-built
  exterior shell (`buildHollowShell`) now both go through the same siding
  material, so hand-drawn buildings get the same finish as AI-generated
  ones.

Not touched: interior partition finishes (already a deliberate clean
off-white per the previous session, and the reference photo is exterior-only
so there's nothing concrete to match there), `aiService.js`'s color/material
prompt guidance (it was already steering toward a two-tone blue body +
dark-navy roof scheme, which is why the reference's palette already lines up
with the offline templates' defaults) — the gap was purely in how the
existing colors got rendered, not which colors get picked.

Scope note: same as above — reviewed and syntax-checked, not run in a
browser. Worth a visual smoke test, especially the roof UV mapping and tree
placement on very small/very large footprints.

## Session 3: the interior pass I skipped in session 2

Called out (correctly) that session 2 only did the exterior. Fixed now,
same "recreate the render engine" approach, not a one-off tint:

- **Interior partition walls** (`getPaintTexture` / `makeInteriorPaintMaterial`
  in `buildParts.js`): tinted fine-grain paint texture instead of one flat
  color — smoother than the exterior siding (no panel seams; real interior
  drywall isn't board cladding), applied to every partition wall whether it
  has a cut-in door or not.
- **Interior floors**: `getFloorTexture` / `makeFloorMaterial` — a
  color-tinted plank texture with staggered end-joints, replacing the flat
  fill color floor slabs had. `buildMesh` now routes any `group: 'interior'`
  part to paint-or-floor by shape (wall-shaped vs slab-shaped, same test the
  interior-door matching already used), instead of the generic material path.
- **Bug I introduced and caught while wiring this up**: `buildWallWithOpenings`
  is shared by manual-modeler exterior walls *and* interior partition walls
  that have a door cut into them (via `buildInteriorWallWithDoors`) — my
  session-2 siding-texture edit would have put exterior board-siding texture
  on interior partition walls with doors. Fixed by branching on the wall's
  own `group` inside that function before picking a material.
- **Interior lighting**: previously one `PointLight` at the whole building's
  bounding-box center — fine for a single room, but rooms away from center
  went dark on anything bigger. Now places one light per distinct room
  (grouped by each mesh's `userData.room` + floor, centroid of that room's
  own parts), falling back to the old single center light only when no part
  in the scene carries room info at all.

Not done: no reference photo for the interior (yours was exterior-only), so
material tones/roughness values here are my best judgment for "reads as a
finished interior," not something matched against an image — flag anything
that looks off once you can see it rendered.

## Session 4: the partitioning itself, not just its finish

You pointed out the room layout doesn't look like a real house — correct.
The house/duplex offline templates (the ones behind the default zero-setup
mode — their colors are what actually produced your reference photo) used
one or two straight walls slicing the whole footprint into equal cells, and
the live-AI fallback for sparse responses did the same thing with a uniform
column/row grid. Real houses don't work that way. Rewrote the generator,
`backend/services/aiService.js`:

- **`buildRealisticFloorPlan(spec, floorNum, envelope)`**: new function that
  builds an actual front-zone/hallway/bedroom-bay plan — living room +
  kitchen clustered near the entry door (unevenly split, living room
  larger), a spine wall with one hallway doorway, then a corridor with
  bedrooms and one noticeably-smaller bath opening directly off it. Detects
  which exterior wall the entry door sits on so the plan orients itself
  correctly regardless of which side the door is on. Falls back to a
  simpler bedroom+bath split (no corridor) on very small footprints where a
  hallway wouldn't make sense.
  - Every room connects to a shared hallway rather than chaining
    room-to-room, and every generated wall gets exactly one doorway — no
    sealed rooms. Verified by running the actual offline `chatDesign()`
    path end-to-end for both the house and duplex templates: matched
    wall/door counts, zero malformed geometry.
- **Fallback partitioner** (`reinforceDesign`, used when live Gemini output
  under-delivers on room planning) now calls the same function instead of
  its own uniform grid code.
- **Offline "Three-Bedroom House" and "Two-Story Duplex" templates**
  (`TEMPLATES.house`, `TEMPLATES.duplex`) rewritten to generate their
  interior via the same function instead of two hardcoded divider walls —
  these are what you're actually seeing without a `GEMINI_API_KEY` set, so
  this was the real fix, not just the fallback.
- **Live-AI prompt** (`schemaInstructions`'s "interior" bullet) updated to
  explicitly describe this front-zone/hallway/bay pattern and explicitly
  tell the model NOT to slice the footprint into a uniform grid — this was
  previously never called out, so a live model could produce the same
  grid-like layout on its own even outside the fallback path.

Not done: this is still a heuristic, not a real floor-plan solver — it
assumes a roughly rectangular footprint and one dominant entry, and won't
handle an L-shaped building or a footprint with two front doors gracefully.
Good enough to fix the "obviously not a real house" complaint; flag it if a
specific shape still comes out wrong.

## Session 5: found why a live-AI result still looked sparse

You shared screenshots of the actual deployed app (arch-build.onrender.com,
`AI: GEMINI` badge — live model, not an offline template) analyzing an
uploaded 3-bed/2-bath blueprint. The 3D result was clearly under-partitioned:
one or two thin walls, nothing resembling the blueprint's actual room count.

Traced it to a real hole in `reinforceDesign`'s safety-net trigger (the
fallback that's supposed to catch exactly this): it only checked how many
*distinct room names* were tagged on a floor (`existingRooms.size >= 3`) and
skipped rebuilding if there were 3+ — with no check that those room tags
were actually attached to enough walls to enclose anything. A sparse Gemini
response that tags three room names onto one or two walls (which is
basically what the screenshot shows) passed that check and was left alone,
un-fixed.

- Added a second condition: count actual wall-shaped interior parts
  (`isWallShapedInterior`, a standalone copy of the same tall-and-thin test
  the frontend renderer uses, since this backend file has no THREE.js
  access) and require roughly one dividing wall per tagged room name before
  trusting the AI's layout as "already planned."
  - Tuned by testing both directions with a small harness (not just eyeballing
    it): a synthetic sparse response (3 room names smeared across 1-2 walls,
    matching the screenshot's symptom) now correctly triggers a rebuild; a
    synthetic reasonably-partitioned response is correctly left untouched.
    First calibration attempt ((rooms−1)×2 walls required) was too strict —
    it would've discarded and rebuilt even good AI layouts and my own
    generator's output — caught by the second test case, not assumed.
- When the fallback does trigger, it now discards the AI's partial attempt
  for that floor (its wall + interior-door parts, not the floor slab) before
  calling `buildRealisticFloorPlan`, instead of layering a full new layout
  on top of a sparse one — which would've left two overlapping, conflicting
  wall schemes.

Important: this fix is in the code in this zip, not yet in what's running
at arch-build.onrender.com — the screenshots you shared are from the
previous deployed version. You'll need to deploy this updated
`backend/services/aiService.js` and re-run the same blueprint upload to see
the corrected layout.
